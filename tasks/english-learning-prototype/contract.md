# 任务契约：英语学习网页可演示原型

## 1. 任务元数据

- **task-id**：`english-learning-prototype`
- **主 Agent role**：`main agent`
- **Coder role**：`coder`
- **Checker role**：`checker`
- **状态**：`accepted`
- **执行顺序**：主 Agent 确认契约后，Coder 实施；Coder 提交后，Checker 独立检查；主 Agent 最终审查并汇报。

## 2. 用户目标

制作一个用于学习英语的网页可演示原型，整体布局参考用户提供的手绘图：左侧为功能入口，主区域展示英语学习功能。第一阶段优先完成可点击、可展示的界面，后续再逐步接入 DeepSeek API、图片识别和 Word 生成。

## 3. Coder 任务

### 3.1 允许读取

- `D:\Project\HTML\AGENTS.md`
- `D:\Project\HTML\roles\coder.md`
- `D:\Project\HTML\tasks\english-learning-prototype\contract.md`
- `D:\Project\HTML\src\` 下与页面实现有关的文件

### 3.2 允许修改

- `D:\Project\HTML\src\` 下实现原型所必需的网页文件。
- 如确有必要，可新增最小数量的页面资源文件，但必须在提交报告中说明原因。

### 3.3 禁止修改

### 3.4 页面功能范围

#### 页面结构

- 左侧竖向功能栏。
- 首个功能入口为“英语”，并处于选中状态。
- 其他功能入口暂留占位状态，不实现具体业务。
- 首页主区域以“单词复习”和“作业批改”两个大卡片作为主要入口；点击后先显示对应上传弹窗，再可进入各自功能页查看详细面板。

#### 单词复习面板

- 提供上传手写图片和印刷文本图片的演示入口。
- 提供示例识别结果或预置单词列表，明确标注为演示数据。
- 提供默写单词、造句、翻译三个复习入口或可点击交互。
- 展示错误较多的单词，并放入“明日重点复习”区域。
- 提供“生成 Word 复习单”的演示按钮；第一阶段可以展示待接入状态或模拟下载流程，但不得伪造真实 API 已调用。

#### 作业批改面板

- 提供上传手写或印刷作业图片的演示入口。
- 覆盖单词、句子和题目三类示例内容。
- 展示批改结果、错误说明和建议修改内容。
- 阅读题示例可展示重点词；没有可靠结果时允许显示空状态。

#### 视觉和交互

- 参考手绘图的左栏加双主面板布局，但使用清晰、可读的网页样式。
- 适配常见桌面窗口宽度；移动端不作为本阶段验收重点。
- 上传、切换复习类型、标记重点和批改结果展示应有可见交互反馈。

#### 首页布局迭代（用户补充要求，2026-10-21）

- 首页文案精简、字号与入口卡片放大，首屏重点呈现“单词复习”和“作业批改”两个醒目的大卡片。
- 桌面双列大卡片高度按用户标注区域约 360px 设计；窄屏可以降低高度并改为单列。
- 点击任一卡片后再打开对应的上传弹窗；弹窗内保留手写/印刷图片的演示选择与文件名反馈。
- 两个大卡片下方展示历史记录区域；记录必须标明演示属性，选中的本地文件只记录文件名等元数据，不读取图片内容、不上传。
- 原有复习、错词、明日重点、批改与阅读重点词演示能力仍可从对应功能入口访问，不要求全部挤在首页。
- 上传弹窗应支持关闭、Escape 关闭及清楚的空状态/选择后反馈。

### 3.5 AI 与安全边界

- 本阶段不要求真实调用 DeepSeek API。
- 可以预留 API 调用函数、配置说明或按钮状态，但不得把密钥硬编码到前端或提交到仓库。
- 不得宣称图片识别、批改或 Word 文件已经由真实 AI 生成，除非确有可复核的实际调用结果。

### 3.6 Coder 验收与提交

- 修改前必须读取实际目标文件。
- 运行适合当前项目的本地验证命令；如果没有构建系统，至少执行 HTML/脚本语法或静态结构检查，并说明命令限制。
- 提交内容必须包括：实际修改文件、每个文件的修改内容、运行命令及真实结果、未解决问题、潜在风险、建议 Checker 重点检查项。
- Coder 只能将状态标记为 `submitted`，不得宣布最终完成。

## 4. Checker 任务

### 4.1 允许读取

- 本契约及项目级 `AGENTS.md`
- `roles\checker.md`
- Coder 实际修改的文件和版本差异
- Coder 报告中列出的验证结果

### 4.2 禁止修改

- 默认不得修改 Coder 的代码、契约或项目规则。
- 如发现问题，只提交返工要求，不直接修复。

### 4.3 独立检查要求

- 查看真实文件内容和差异，不能只相信 Coder 的文字总结。
- 独立运行可复现的测试、构建或静态检查命令。
- 检查是否越过允许文件范围、是否引入不必要依赖、是否暴露密钥、是否遗漏关键交互。
- 检查布局是否包含左侧功能栏、单词复习和作业批改两个主面板。
- 检查上传入口、复习类型、明日重点、批改结果和阅读重点词状态是否可演示。

### 4.4 Checker 输出

结论只能是：`ACCEPTED`、`REJECTED` 或 `NEEDS_USER`。

报告必须包括：原始目标、实际检查文件、实际差异、运行命令及结果、发现的问题、范围检查、最终结论；若拒绝，还要列出明确返工要求。

## 5. 主 Agent 职责

- 在用户审查通过前保持 `pending_user_review`，不启动 Coder 或 Checker。
- 审查 Coder 的提交和 Checker 报告，不把 Coder 的“已完成”直接视为最终完成。
- Checker 为 `REJECTED` 时退回 Coder；为 `NEEDS_USER` 时向用户提问；只有证据充分且检查通过后才能向用户汇报。
- 最终汇报必须包含用户目标、完成任务、实际修改文件、验证结果、Checker 结论、剩余风险和下一步建议。

## 6. 明确不做

- 不实现登录、用户系统、云端同步或其他左侧功能的具体业务。
- 不在本阶段要求真实 DeepSeek 调用、稳定的 OCR、长期错题数据库或生产级 Word 排版。
- 不伪造任何 API 调用、识别结果、批改结果、下载文件或测试结果。

1. Coder 与 Checker 按本契约所列任务边界执行。
